# Agent Runtime SDK 与外层平台的职责边界

> 状态：已明确的设计方向。整理日期：2026-10-04。

## 目标与背景

平台是供多个用户、多个部门共享的云端 SaaS。核心设计借鉴讨论中提到的 pi Agent 极简、可扩展思路：把单个 Agent 的执行循环抽成 SDK，基础设施和 SaaS 管理放在外层。本篇不对 pi Agent 的具体代码实现作判断。

核心 loop 根据上下文请求模型，执行模型选择的工具，把工具结果放回上下文，然后继续，直到完成、失败、取消或达到执行限制。等待审批等暂停行为可以扩展，不应被误判为正常完成。

前端连接的生命周期与运行的生命周期分离。页面刷新、SSE 断开不终止运行；用户主动停止通过独立的取消请求传达给后端。

## 分层职责

| 层次 | 负责 | 不负责 |
| --- | --- | --- |
| Runtime SDK | 单 Agent loop、模型与工具调用编排、上下文、事件语义、恢复状态、从恢复点继续 | DB、Redis、SSE、Pod 调度、租户基础设施 |
| 外层运行管理 | 创建运行、持久化、任务分配、心跳、接管、取消、执行归属检查 | 复制一套模型与工具循环逻辑 |
| 工具执行层 | 实际调用内部服务或 MCP、身份与权限校验、凭据注入、超时和幂等策略 | 管理前端连接 |
| API 与事件服务 | 接受用户请求、鉴权、读取历史、SSE 传输、重连展示 | 通过连接是否存在决定运行是否继续 |

这是逻辑分层，不要求初期分别部署成多个服务。

## SDK 与恢复机制的分界

SDK 最了解执行过程，因此由 SDK 定义哪些状态足够恢复、哪里是安全恢复点，以及给定状态后下一步做什么。

外层决定何时保存、保存在哪里、何时重新启动，并把加载出的状态传回 SDK。持久化细节留在外层，但关键保存的成功或失败必须反馈给 SDK。

建议区分三类扩展接口：

- **依赖接口**：模型适配器、工具执行器、上下文构建器。
- **控制接口**：取消、执行授权检查、必要的审批等，需要明确影响执行流程。
- **输出接口**：可丢失的实时事件，以及必须等待保存成功的恢复状态。

普通显示回调失败或前端断开不应中止执行。关键恢复点保存失败则应停止推进，避免执行不断前进却没有可靠进度。取消与失去执行权的信号应能传入 SDK；SDK 不需要知道信号来自 Redis 还是其他设施。

## “一切皆工具”的落地边界

模型看到的是工具名称、说明和参数结构。实际执行统一交给工具执行器，内部工具与 MCP 工具可以实现相同抽象。

平台仍需区分：

- 工具定义：模型能理解和选择什么。
- 工具执行：路由、超时、错误、结果。
- 工具治理：租户授权、凭据、配额、审计及必要审批。

向模型提供了工具定义，不等于可以跳过调用时鉴权。工具列表不承担安全边界；实际调用按用户、租户和执行身份检查。

## 多租户约束

会话、运行、结果、文件和工具资源都要有明确的租户归属。租户并发、排队和预算在外层管理，避免单一部门占满共享资源。

普通远程工具调用可以共享 Worker 的有界并发。用户代码或 shell 等执行能力需要另行设计沙箱；并非每个 Agent 都天然要求独立容器。具体调度和沙箱方案尚未确定。
