# 通过执行尝试隔离降低锁风险

> 状态：降低锁风险是已明确目标；本篇数据模型与流程是讨论末尾提出的待确认方案，尚未得到实现验证。整理日期：2026-10-04。

## 已明确的约束

event 表预计会很大。设计需要避免长期持锁、围绕大量事件做加锁更新，以及把安全性完全建立在开发者不会漏掉某次检查的假设上。

希望采用先抢到者执行的方式，将竞争控制缩小到短暂、有限的原子操作；为旧 Worker 延迟停止等实现偏差预留容错空间。

“减少锁风险”不等于数据库内部绝不使用锁。条件更新可能产生短暂行锁，关键是只操作小型运行记录、缩短事务，并且绝不把模型请求或工具执行放进持锁事务。

## 核心建议：隔离错误写入的影响

与其要求旧 Worker 绝不写入任何事件，可以允许它追加自己的旧尝试事件，但这些事件不能进入新尝试的上下文、展示或终态。

| 概念 | 职责 |
| --- | --- |
| `conversation` | 长期会话及其消息关系 |
| `run` | 一次用户请求对应的逻辑执行；保存当前有效 `attempt_id` |
| `attempt` | 一次实际执行尝试；记录父尝试和固定继承的恢复点 |
| `event` | 追加写入，始终绑定产生它的 `attempt_id` |
| `checkpoint` | 完整、不可变或可精确版本定位的恢复状态 |

这些是逻辑实体，不要求第一版全部建成独立物理表。

## 为什么必须继承固定恢复点

假设 A 在恢复点 C 后失联，B 从 C 接管。B 应读取 C 的完整快照，或严格重放截至 C 的确定事件范围，不能动态继承“A 的最新全部事件”。

```text
attempt-A：输入 → 模型响应 → 工具 A 完成 → 恢复点 C → 失联 → 迟到事件
                                                    │
attempt-B：                                         └→ 从 C 继续
```

A 恢复后产生的迟到事件仍属于 A，不会改变 C，也不会被自动并入 B。前端读取当前尝试及其固定继承的历史，避免一会儿显示 A、一会儿显示 B。

## 接管流程示意

1. Redis 超时判断和原子抢占筛选接管者。
2. 创建候选 attempt，准备新的执行身份。
3. 在一个短 DB 事务中，条件切换 Run 的当前 attempt，并选择、固定已经完整提交的恢复点；竞争失败的请求退出。
4. 事务提交后确认 Redis 执行身份仍匹配，才启动 SDK。协调步骤不完整时不执行，后续通过重试恢复。
5. 新 Worker 将事件追加到新 attempt，按照新身份发送心跳。

当前尝试的切换可表达为：

```sql
UPDATE runs
SET active_attempt_id = :new_attempt
WHERE id = :run_id
  AND active_attempt_id = :expected_old_attempt;
```

受影响行数为一表示切换成功；为零表示竞争失败。这里省略了租户、运行状态和恢复资格等条件，是示意代码，不能直接作为完整接管实现。

实际操作还需要保证候选 attempt、固定恢复点和 Run 切换在 DB 内部一致。事务只包含数据库操作；不等待 Redis、模型或工具。失败候选记录可以回滚或保留为未启动状态，不得因存在候选记录就开始执行。

Redis 与 DB 不需要组成一个分布式事务。出现 Redis 抢占成功但 DB 切换失败时，退出且只按匹配令牌清理自身记录；DB 切换成功但 Worker 尚未启动就崩溃时，该尝试可以在超时后再次被接管。

## event 表的写入边界

事件按 attempt 追加，不为每条事件先锁住整个 Run，也不更新历史大批量事件。索引与读取范围围绕租户、Run、attempt 和游标设计，避免全表扫描。

旧 Worker 必须一直使用创建时取得的 attempt 身份写入，不能重新读取 active attempt 后把旧结果写到新尝试中。这个约束应封装在执行上下文和存储接口里。

工具完成、模型完成和错误也应归属于 attempt。更新 Run 的最终状态、当前结果或其他共享投影时，仍需以当前 attempt 为条件，防止旧 Worker 覆盖全局有效状态。事件隔离不等于允许无条件修改共享记录。

## 能保证什么，不能保证什么

该设计能容忍旧 Worker 晚停一段时间，甚至追加少量无效事件，而不污染新执行的有效历史。存储会多出一些被放弃尝试的数据，可保留用于审计或按策略清理。

它不保证任何时刻都只有一个进程消耗算力，也不保证外部工具只执行一次。已经发出的调用仍需幂等、结果查询或人工确认。旧 Worker 发现失去身份后仍应尽快退出。

只有真正按 attempt 隔离读取、恢复与共享状态更新，才能获得上述效果；仅给 event 表加一个字段不够。

## 待确认事项

- 是否接受旧 attempt 留下少量不再生效的事件，以换取简单的追加写路径。
- 恢复点采用完整快照还是可定位的事件边界，以及对应的保留策略。
- 手动恢复是否为第一版唯一入口，是否需要自动接管。
- Redis 与 DB 协调中途失败后的重试、核对与告警策略。
- 同一会话内新用户输入、恢复和取消请求的并发规则。
