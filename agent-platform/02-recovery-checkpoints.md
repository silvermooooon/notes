# 恢复语义与安全恢复点

> 状态：已明确的设计方向。整理日期：2026-10-04。

## 恢复目标

允许一次执行因工具失败、进程退出或其他异常中断。重新发起时，尽量复用已经完成的工作，以较低实现复杂度减少损失，不要求恢复进程的内存现场。

“任意时刻恢复”指用户可以随时发起恢复，系统从最近一个完整、可靠的执行边界继续；不承诺从任意 token 或工具内部指令精确续跑。手动恢复已能满足讨论中的基本需求，是否自动接管仍可另行决定。

后续明确的取舍是：高频实时增量可以不持久化。因此，“可恢复”主要针对完整执行状态，并不要求逐个重放所有已经展示过的增量事件。

## 安全恢复点

| 边界 | 应可靠保存的内容 | 恢复行为 |
| --- | --- | --- |
| 接受输入 | 本轮输入、所需的运行配置引用 | 可以重新启动本轮 |
| 模型完整响应 | 完整结构化消息、工具调用 ID、名称和参数 | 复用响应，进入工具执行或完成流程 |
| 每个工具完成 | 调用 ID、结果或明确错误、已完成进度 | 复用已保存结果，处理剩余调用 |
| 运行结束 | 最终消息、完成／失败／取消等状态 | 展示终态，不继续执行 |

示例：模型计划执行 A、B 两个工具；A 的结果已经保存，B 执行中故障。恢复时复用模型响应和 A 的结果，单独处理 B，不必重做整轮。

恢复状态必须足够组成合法的模型上下文，并指出下一步动作。不能只有用户可见的最终文本。配置和工具定义的版本或必要引用也要能关联起来；不应把凭据明文塞进恢复状态。

恢复状态的结构与推进规则由 SDK 定义，保存与加载由外层实现。关键状态保存成功后，SDK 才推进到下一步。

## 内容保存与执行恢复的区别

半截模型文本可以用于临时显示，但不一定构成可继续执行的模型响应。若生成未完成，本设计允许丢弃该次未完成生成并重做模型请求。

已经保存完整响应，则直接复用。前端刷新只恢复观看，不应自动触发重新执行；只有恢复流程取得执行权后，才启动新的执行尝试。

## 工具执行结果未知

工具已产生外部效果、但结果尚未保存时，Worker 可能退出。此时持久化状态只能证明调用曾经开始，不能证明它没有成功。

- 查询类工具或支持幂等键的工具，可以按策略重试。
- 有副作用、无法安全重试的工具，需要核实结果或人工确认。
- 已明确记录的失败可以按工具策略处理；结果未知不能直接当作失败重试。

若同一次逻辑工具调用跨恢复尝试重试，幂等身份应保持稳定，不能因为新建执行尝试就自动更换幂等键。

工具是否支持安全重试由工具执行层声明，SDK 按该策略继续或暂停。心跳、执行令牌和恢复点均不能撤销已经发出的外部操作。

## 停止与终态

取消请求已接收和执行已停止是两个不同阶段。取消应传递给模型请求和工具执行，但不承诺撤销已经完成的工具效果。

失败不能只靠临时文本通知前端；明确失败、取消和正常完成都需要可靠记录。Worker 突然消失时由外层心跳机制识别，不要求已经失联的 Worker 自行写下失败记录。
