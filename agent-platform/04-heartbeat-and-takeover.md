# Redis 心跳、执行归属与接管

> 状态：Redis 心跳与抢占方向已明确；与 DB 的最终协调方式见第五篇待确认方案。整理日期：2026-10-04。

## 目标

前端可能连接到任意 Pod，需要知道原 Worker 是否仍在运行。心跳和高频状态查询放在 Redis，避免每次查询和续期都访问 DB。

监测对象是具体运行／执行尝试，而非仅仅 Pod。Pod 存活不能证明某次 Agent 执行仍正常；心跳正常也不能证明模型或工具没有卡住，具体调用仍需要超时。

## 心跳记录

每个 Run 对应一个 Redis key，可包含：

| 字段 | 含义 |
| --- | --- |
| `owner_id` | 当前负责执行的 Worker 实例身份 |
| `attempt_token` | 本次取得执行权的唯一令牌 |
| `heartbeat_at` | 最近一次有效心跳时间 |
| `data_version` | 已提交到 DB 的数据版本／游标 |

讨论中的初始参数为每 5 秒更新一次，超过 15 秒未更新允许进入接管流程。这是待实践验证的参数，不是适用于所有负载的固定标准。

时间比较宜使用统一的 Redis 时间来源或等价的租约 TTL，避免各 Pod 时钟偏差。Redis 访问失败与明确检测到租约过期需要区分：访问失败意味着状态未知，不能直接将所有 Run 判定为失联并重新启动。

## 超时的含义

超过阈值意味着旧 Worker 没有及时证明自己活跃，足以触发恢复判断；不意味着确定它已经死亡。网络中断或进程暂停后，旧 Worker 仍可能恢复。

接管后必须能识别新旧执行身份。只用 Pod ID 不够：同一 Pod 可能先后承载同一个 Run 的不同执行尝试，因此需要独立令牌。

## 抢占与续期的原子性

“先拿到者执行”需要原子的条件操作，不使用先读后无条件覆盖的实现。

- **抢占**：在一次原子操作内检查原 owner、令牌和超时条件，满足时写入新 owner、新令牌和心跳。
- **续期**：仅当令牌仍匹配时更新心跳和所属尝试的数据版本。
- **释放**：仅当令牌匹配时删除或结束自己的记录。

可以用短小的 Redis Lua 脚本实现。旧 Worker 不能拿旧快照覆盖整个 key，把执行身份改回自己。多个恢复请求同时发现超时，不代表它们都获得执行权。

这些操作没有跨模型请求或工具调用持有的应用锁；但原子竞争本身不可省略。仅靠普通读写无法排除竞争。

## 旧 Worker 恢复后的行为

Worker 在心跳、启动新步骤和保存可靠状态等边界检查执行身份。确认失去执行权后停止推进，并尝试取消进行中的请求；前端事件也携带执行身份，避免旧输出污染新尝试。

检查后仍可能发生接管，已经发出的工具调用也不会自动撤销。因此，仅靠“先检查令牌，再写 DB”不能消除所有竞争；DB 必须有自己的有效执行选择或条件提交机制。

讨论过两种方式：

1. 严格提交校验：在同一个 DB 事务中校验执行令牌并保存结果。
2. 执行尝试隔离：旧执行仍可能追加自己的事件，但新尝试只继承固定恢复点，不受旧追加影响。

由于希望减少锁操作和 event 表风险，第二种是当前建议，详见[执行尝试隔离](05-attempt-isolation.md)。不应把两种方式混写成已经确定的单一实现。

## Redis 与 DB 的边界

Redis 保存高频活跃状态和数据更新提示。DB 保存完整结果、恢复点、终态，以及少量决定有效执行的记录。

Redis 锁不能被假定为在所有故障下都提供唯一执行保证。例如使用异步复制的主从切换方案时，尚未复制的锁记录可能丢失。因此建议让低频 DB 条件更新最终确认当前有效尝试，而不是只依赖 Redis owner。[Redis 官方分布式锁说明](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)

手动恢复和自动恢复可以复用相同接管协议。正常前端重连只订阅运行，不应无条件创建第二个 Worker。
