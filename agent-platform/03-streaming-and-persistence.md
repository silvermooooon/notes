# 实时事件、持久化与 SSE 重连

> 状态：已明确的设计方向。整理日期：2026-10-04。

## 核心取舍

当前接入主要使用 Responses API。本篇按讨论中的应用层抽象区分“增量文本”和“完整输出”，不绑定具体 API 事件名称。

增量文本为前端提供打字机效果；完整输出用于可靠展示与执行恢复。不逐条持久化高频增量，避免重复保存同一内容和大量细碎写入。

可接受的体验是：正常本地订阅提供流式显示；跨 Pod 重连可以退化为等待本次模型调用完成后，一次显示完整结果。

## 两条输出通道

| 通道 | 内容 | 可靠性与处理 |
| --- | --- | --- |
| 实时事件 | 文本增量、临时显示信息 | 尽力发送；不落 DB；订阅失败不影响 Runtime |
| 可靠状态 | 完整模型响应、工具计划和结果、恢复点、终态 | 保存失败必须反馈给 Runtime；关键步骤保存成功后再推进 |

实时增量可以在持久化之前被用户看到，因此进程故障后允许丢失这部分未完成内容。这是明确的体验取舍，不承诺所有已显示字符都能恢复。

DB 保存的完整输出必须保留执行所需的结构，而不仅是渲染后的文本。工具结果和错误状态同样属于可靠数据。

## 正常连接与重连

前端 SSE 与 Worker 的模型请求是两条独立连接。断开前者不终止后者，也不让 Worker 等待前端重新上线。

### 连接到 Worker 所在 Pod

外层把 SDK 的实时事件直接转发给本地订阅者。前端先获得已保存历史，再持续渲染当前消息。

同 Pod 重连也不天然拥有之前的增量。可以在内存维护当前消息快照，并确保快照与后续增量之间没有遗漏或重复；如果不实现这个衔接，也可以直接降级为等待完整输出。

### 连接到其他 Pod

新 Pod 从 DB 读取完整历史，通过 Redis 了解运行是否活跃以及已提交数据是否更新。没有跨 Pod 增量转发时，前端显示等待状态，完整结果落库后再一次性显示。

跨 Pod 实时总线不是本阶段的必要条件；亲和路由也不是恢复正确性的前提。

## 防止前端重复显示

消息应有稳定 ID，增量和完整结果指向同一消息。完整结果到达时，替换对应临时内容，不再追加一份重复文本。

若采用执行尝试模型，事件还应携带 `attempt_id`，前端确认执行切换后忽略旧尝试的增量。持久化内容的版本与增量序号分开，不声称可以按 DB 版本重放未保存的 token。

## 数据版本与读取压力

Worker 只有在 DB 提交成功后，才能把 Redis 中的数据版本推进到对应进度。心跳版本应表示“已保存的进度”，不能表示“准备保存的进度”。

新 Pod 可以高频读 Redis，仅在版本变化时增量读取 DB。若版本更新合并进每五秒一次的心跳，跨 Pod 看到完整结果也可能多等待一个心跳间隔；是否在提交后即时更新属于实现取舍。

DB 提交与 Redis 更新不是同一个事务，可能出现 DB 已写入但 Redis 未更新。因此不能把 Redis 通知当作唯一事实来源。重连、发现失联、终态确认或低频核对时，需要有 DB 校准路径，避免结果已经保存却一直不显示。具体频率尚未确定。
